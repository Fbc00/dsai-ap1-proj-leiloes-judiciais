# Banco no Supabase — Plano de Implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Permitir que o backend use um projeto Supabase (plano Free, vazio) como Postgres, apontado só por env, com SSL obrigatório fora do Postgres local, roles próprias, RLS em todas as tabelas e `/api/health` que acusa banco fora do ar.

**Architecture:** O Supabase é usado **só como Postgres**. Auth, Storage, Data API, Realtime e Edge Functions não são usados. O backend conecta pelo **Supavisor em session mode** (`aws-<n>-<regiao>.pooler.supabase.com:5432`, usuário `<role>.<project-ref>`) com o driver `asyncpg` e `?ssl=require`. Duas roles nossas, criadas uma vez por `src/docker/supabase/01-roles.sql`: `leiloes_owner` (roda migrations, dona das tabelas) e `leiloes_app` (só DML). A migration `0007` revoga as roles da Data API (`anon`, `authenticated`, `service_role`) e liga RLS em todas as tabelas, com a policy `acesso_app` liberando tudo pra `leiloes_app`. A autorização (admin/operador) continua no código. O RLS vale em todos os ambientes. Dev, CI, pytest e e2e continuam no Postgres 16 local do compose.

**Exemplo do Supabase (SQLAlchemy + psycopg2), adaptado:**

| Exemplo da doc | Aqui | Por quê |
|---|---|---|
| `postgresql+psycopg2://...?sslmode=require` | `postgresql+asyncpg://...?ssl=require` | Stack async; psycopg2 seria dep nova e síncrona. Conferido no container (SQLAlchemy 2.1.1): `sslmode=require` chega ao `asyncpg.connect` como kwarg `sslmode`, que o asyncpg não aceita. |
| `load_dotenv()` + `os.getenv(...)` | `Settings` (pydantic-settings) já lê o `.env`; URL inteira em `DATABASE_URL` | Fonte única de env; `python-dotenv` não é dep aprovada. |
| `try: engine.connect()` / `print` | `GET /api/health` faz `SELECT 1` via `Depends(get_session)` e responde `503` | Projeto Free pausado ou credencial errada aparece no health, não na primeira tela. O `lifespan` não muda (no Python Worker ele roda a cada request). |
| `poolclass=NullPool` | pool padrão do SQLAlchemy | Processo longo; pool padrão (5 + 10) cabe nos 200 clientes do pooler do Free. |

**Tech Stack:** FastAPI · SQLAlchemy 2.1 async + asyncpg · Alembic · pydantic-settings · Postgres 16 (local) · Supabase Postgres (Supavisor session mode) · `postgres:17-alpine` (psql/pg_dump no ensaio e nos docs) · pytest.

**Spec:** `SPEC/2026-10-01-backend.md` (§1 grants, §3 `GET /health`, §6 permissão de banco) e `SPEC/2026-10-01-infra.md` (§1 arquivos, §2 Postgres). Cada task começa atualizando a seção da spec que ela muda (policy do repo: spec primeiro). Contexto: `SPEC/2026-10-01-visao-geral.md`. Convenções: `CLAUDE.md` raiz e `src/backend/CLAUDE.md`.

**Decisões fechadas (grilling):**

2. Só banco. Deploy (Worker), `docker-compose.prod.yml` e `.github/workflows/deploy.yml` **não mudam** neste plano.
3. Sem backup automático. README documenta `pg_dump`/`pg_restore` manuais.
4. Migrations no Supabase rodam como `leiloes_owner` (role dedicada), não como `postgres`.

```python
    @model_validator(mode="after")
    def exige_ssl_fora_do_local(self) -> Self:
        urls: dict[str, str] = {
            "DATABASE_URL": self.DATABASE_URL,
            "DATABASE_URL_MIGRATOR": self.DATABASE_URL_MIGRATOR,
            "DATABASE_URL_TEST": self.DATABASE_URL_TEST,
        }
        for nome, valor in urls.items():
            if not valor:
                continue
            url = make_url(valor)
            if url.host is None or url.host in HOSTS_LOCAIS:
                continue
            if "sslmode" in url.query:
                raise ValueError(f"{nome}: use ?ssl=require (asyncpg), não sslmode")
            if url.query.get("ssl") not in SSL_SEGURO:
                raise ValueError(f"{nome} precisa de ?ssl=require fora do Postgres local")
        return self
```
