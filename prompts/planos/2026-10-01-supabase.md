# Postgres de produção no Supabase — Plano de Implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Trocar o Postgres do `docker-compose.prod.yml` pelo Postgres gerenciado do Supabase, sem mudar auth, ORM, migrations nem contrato de API. Junto, endurecer o ciclo de vida do banco no FastAPI: SSL obrigatório em prod, pool configurável, `lifespan` que testa a conexão no startup e `/api/health` que consulta o banco.

**Architecture:** O Supabase é usado **só como Postgres**. Auth, Storage, Data API (PostgREST), Realtime e Edge Functions ficam desligados ou sem uso. O backend conecta pelo **Supavisor em session mode** (`aws-0-<regiao>.pooler.supabase.com:5432`, usuário `<role>.<project-ref>`) com `asyncpg` e `?ssl=require`. Duas roles continuam: `leiloes_app` (DML, criada uma vez por SQL) e `postgres` (migrations, papel do antigo `leiloes_owner`). A migration `0007` revoga o acesso das roles da Data API (`anon`, `authenticated`, `service_role`) às tabelas do `public`, como defesa em profundidade além da Data API desligada no dashboard. Dev, CI, pytest e e2e continuam no Postgres 16 local do compose.

**Exemplo do Supabase (SQLAlchemy + psycopg2), adaptado ao nosso contexto:**

| Exemplo da doc | Aqui | Por quê |
|---|---|---|
| `postgresql+psycopg2://...?sslmode=require` | `postgresql+asyncpg://...?ssl=require` | Stack é async (asyncpg já aprovado; psycopg2 seria dep nova e síncrona). Conferido no container (SQLAlchemy 2.1.1): `sslmode=require` chega ao `asyncpg.connect` como kwarg `sslmode`, que o asyncpg não aceita. O certo é `ssl=require`. |
| `load_dotenv()` + `os.getenv("user")`... | `Settings` (pydantic-settings) já lê `.env`; URL inteira em `DATABASE_URL` | Fonte única de env; `python-dotenv` não é dep aprovada. |
| `create_engine(...)` global | `criar_engine(settings)` + `get_engine()` cacheado, aberto/fechado no `lifespan` do FastAPI | Ciclo de vida do app ASGI; `engine.dispose()` no shutdown. |
| `poolclass=NullPool` com pooler | `QueuePool` pequeno (`DB_POOL_SIZE`, `DB_MAX_OVERFLOW`) | uvicorn é processo longo; NullPool faria handshake TLS até a região do Supabase a cada request. Em session mode cada conexão do pool ocupa uma do Supavisor, então o pool é dimensionado pelo `Pool Size` do projeto. |
| `try: engine.connect()` / `print` | `lifespan` faz `SELECT 1` no startup; `GET /api/health` faz `SELECT 1` via `SessionDep` e responde `503` se falhar | Deploy (`curl -fsS /api/health`) passa a pegar credencial/host errado. |

**Tech Stack:** FastAPI (lifespan, `Annotated[..., Depends()]`, `dependency_overrides`) · SQLAlchemy 2.1 async + asyncpg · Alembic · pydantic-settings · Docker Compose · Supabase Postgres 17 (Supavisor session mode) · `postgres:17-alpine` (pg_dump/psql) · pytest.

```python
        if self.APP_ENV != "prod":
```

```sh
dump="$1"

  echo "COMMIT;"
```

````markdown
Produção (um servidor, imagens do GHCR, banco no Supabase):

1. No Supabase: crie o projeto (região `sa-east-1`), anote o *project ref*. Em **Integrations → Data API**, desligue **Enable Data API**. Em **Database → Settings**, ligue **Enforce SSL** e adicione o IP do servidor em **Network Restrictions**.
2. Crie a role da aplicação (do seu shell; senhas não vão pro repositório):

   ```bash
   cd src
   read -rs SENHA_POSTGRES; read -rs DB_APP_PASSWORD
   docker run --rm -i -e PGPASSWORD="$SENHA_POSTGRES" postgres:17-alpine \
     psql "host=aws-0-<regiao>.pooler.supabase.com port=5432 dbname=postgres user=postgres.<ref> sslmode=require" \
     -v ON_ERROR_STOP=1 -v senha_app="$DB_APP_PASSWORD" < docker/supabase/01-roles.sql
   ```

3. No `src/.env` do servidor:

   ```
   DATABASE_URL=postgresql+asyncpg://leiloes_app.<ref>:<DB_APP_PASSWORD>@aws-0-<regiao>.pooler.supabase.com:5432/postgres?ssl=require
   DATABASE_URL_MIGRATOR=postgresql+asyncpg://postgres.<ref>:<SENHA_POSTGRES>@aws-0-<regiao>.pooler.supabase.com:5432/postgres?ssl=require
   SUPABASE_DB_HOST=aws-0-<regiao>.pooler.supabase.com
   SUPABASE_DB_USER=postgres.<ref>
   SUPABASE_DB_PASSWORD=<SENHA_POSTGRES>
   DB_POOL_SIZE=3
   DB_MAX_OVERFLOW=2
   ```

   - URLs asyncpg usam `ssl=require` (nunca `sslmode`); a API não sobe em prod sem isso.
   - Senha com `@ / # % :` vai percent-encoded na URL (`@` → `%40`, `/` → `%2F`, `#` → `%23`). Em `SUPABASE_DB_PASSWORD`, `$` vira `$$` (interpolação do compose).
   - Conexões: `2 workers × (DB_POOL_SIZE + DB_MAX_OVERFLOW) + 2` (migrate e backup) ≤ **Pool Size** em *Database → Settings → Connection pooling*.

4. Suba: `cd src && docker compose -f docker-compose.prod.yml up -d`. O serviço `migrate` aplica as migrations como `postgres`; o backend só sobe se conectar (`/api/health` responde `503` se o banco cair).
````

````markdown
## Backup e restore (produção)

O serviço `backup` do `src/docker-compose.prod.yml` grava diariamente no volume `backups`:
`pg-<data>.dump` (dados do schema `public` do Supabase, `pg_dump -Fc --data-only`), `pg-<data>.revisao` (revisão alembic do dump) e `media-<data>.tgz` (PDFs e e-mails), retenção `BACKUP_RETENCAO_DIAS` (default 7). O schema vem das migrations.

Copiar os backups pra fora do host:

```bash
cd src && docker compose -f docker-compose.prod.yml cp backup:/backups ./backups-copia
```

Restaurar o banco (substitui todos os dados, tudo ou nada; o banco precisa estar na revisão do `.revisao`):

```bash
cd src
docker compose -f docker-compose.prod.yml run --rm migrate
docker compose -f docker-compose.prod.yml exec backup sh /restore.sh /backups/pg-<data>.dump
```

Dump de fora do volume: `docker compose -f docker-compose.prod.yml cp pg-<data>.dump backup:/backups/` (e o `.revisao` junto) antes do restore.

Restaurar a mídia:

```bash
cd src && docker compose -f docker-compose.prod.yml run --rm --no-deps --entrypoint tar -v "$PWD/media-<data>.tgz:/b.tgz:ro" backend xzf /b.tgz -C /data
```

Rollback de versão: `cd src && IMAGE_TAG=sha-<anterior> docker compose -f docker-compose.prod.yml up -d`.
````

